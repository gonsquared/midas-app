# Runbook: Diagnose common API failures

- **Owner:** backend maintainers
- **Last verified:** 2026-10-19, against the local Docker stack (`docker compose up`) and the automated API tests; the log and metric names below are asserted by tests in `apps/api`
- **Severity / urgency:** routine triage; treat a failing `/health` in production as urgent

## When to use this

Users report errors or slowness, an alert fires on `/health` or `/metrics`, or the API logs show
`unhandled error` or `audit write failed` lines. Start with [Triage](#triage) and jump to the
matching entry in [Troubleshooting](#troubleshooting).

## Before you start

- Shell access to the host running the API container (examples use `docker compose`; on a
  platform with its own log viewer use that instead).
- The `METRICS_TOKEN` value (secret store or the deployment environment) if you want metrics.
- The request id from the user report, if there is one. Every API response, success or error,
  carries it in the `X-Request-Id` header, and error bodies repeat it as `requestId`.

## How requests are correlated

- Every response has `X-Request-Id`. A client may send its own, which is kept only if it matches
  `^[A-Za-z0-9-]{8,64}$`; otherwise the server generates a UUID.
- Every log line of a request (including `request completed`) has `requestId`, which is that
  value, and `serverRequestId`, a UUID always generated by the server. Audit log rows store the
  `serverRequestId`, never the client-supplied id, so a client cannot forge audit correlation.
- Logs are JSON, one object per line. Authorization headers, cookies, passwords and tokens are
  redacted, and query values are never logged.

## Steps

### Triage

1. Check liveness and database readiness.

   ```bash
   curl -s -i http://localhost:3000/health
   ```

   Expected: `200` and `{"status":"ok","version":"...","uptimeSeconds":N,"checks":{"database":"up"}}`.
   `503` with `"database":"down"` means go to "Database unreachable".

2. Find what happened to one request, using its id.

   ```bash
   docker compose logs api --no-log-prefix | grep '"requestId":"<id from the user>"'
   ```

   Expected: a `request completed` line with `res.statusCode` and `responseTime`, plus any
   `request rejected` (client error) or `unhandled error` (server error, with `err`) lines.

3. Look at the recent error rate (level 50 is `error`, 40 is `warn`).

   ```bash
   docker compose logs api --since 15m --no-log-prefix | grep -E '"level":(40|50)'
   ```

4. Scrape metrics (only when `METRICS_TOKEN` is set; otherwise `/metrics` answers 404).

   ```bash
   curl -s -H "Authorization: Bearer $METRICS_TOKEN" http://localhost:3000/metrics
   ```

   Useful series:

   | Metric | Meaning |
   | --- | --- |
   | `midas_http_requests_total{method,route,status}` | Requests by matched route pattern; watch 5xx status codes and `429` (the `status` label is the exact code) |
   | `midas_http_request_duration_seconds` | Latency histogram per route |
   | `midas_db_pool_connections` | Pool state (in use, idle, waiting) |
   | `midas_audit_write_failures_total` | Audit events that could not be written; must stay 0 |
   | `midas_scheduler_runs_total`, `midas_recurring_occurrences_total` | Recurring job health |
   | `midas_process_uptime_seconds` | A small value means a recent restart or crash loop |

## Verify

After applying a fix: `/health` returns `200` with `database: up`, a new request produces a
`request completed` line with a 2xx/4xx status, `midas_audit_write_failures_total` stops growing,
and the error log filter from step 3 goes quiet.

## Roll back

These are diagnostic steps. The only changes proposed below are configuration edits (environment
variables) and restarts. Restore the previous value of any variable you changed and restart the
`api` service again.

## Troubleshooting

| Symptom | Likely cause | Fix |
| --- | --- | --- |
| `/health` returns 503, `database: down` | Database container stopped, wrong `DATABASE_URL`, TLS mismatch (`DATABASE_SSL`), pool exhausted | `docker compose ps db`; `docker compose logs db`; verify `DATABASE_URL` and `DATABASE_SSL` (production defaults to `verify-full`, which needs `DATABASE_SSL_CA` for a private CA); restart `db` then `api` |
| API will not start; log shows a config error naming a variable | Invalid or missing env var (boot fails fast and names the variable, never its value) | Fix the named variable against `.env.example`, restart. Production rejects placeholder secrets |
| Users get `429` and `Retry-After` | A rate limit was hit: login (per IP+email, per IP, per account), register, forgot/reset, refresh, per-user read/write, export, global per IP | Wait for `Retry-After` seconds. If every user shares one limit, `TRUST_PROXY` is wrong (the API sees the proxy address): set it to the number of proxy hops. Tune `RATE_LIMIT_*` maxima only for a real traffic need, then restart. Counters are in memory, so a restart also clears them |
| Account locked out of login after attackers guess its email | Per-account limiter (`RATE_LIMIT_LOGIN_ACCOUNT_MAX` per hour) | Wait for the window, or restart the API to clear counters in an emergency (this clears everyone's counters) |
| Browser shows a CORS error | Dev only: the origin is not in `CORS_ORIGINS`. In production the SPA is same-origin and no CORS headers are sent | Add the exact origin (`scheme://host[:port]`, no path, no wildcard) to `CORS_ORIGINS` and restart |
| Browser blocks scripts or styles (CSP violations in the console) | A change introduced inline script/style or a third-party origin; the CSP is strict (`self` only) | Remove the inline code or third-party use; do not loosen the CSP. See "Content Security Policy" in CONTRIBUTING.md |
| `/metrics` returns 404 | `METRICS_TOKEN` is unset (endpoint disabled by design) | Set `METRICS_TOKEN` (at least 32 characters) and restart |
| `/metrics` returns 401 | Missing or wrong bearer token; the query string is not accepted | Send `Authorization: Bearer <token>`. Repeated failures from one IP end in 429 |
| `500` responses with `INTERNAL_ERROR` | Unexpected exception; the body is generic by design | Search the logs for the `requestId` from the response; read the `unhandled error` line (`err`) |
| Password reset or other emails never arrive | Mail transport misconfigured or SMTP down; sending runs after the response, so the API still answers 2xx | Check `MAIL_TRANSPORT`, `SMTP_*`; look for `background task failed` lines; locally open Mailpit |
| `midas_audit_write_failures_total` increasing | Audit insert failing (database permission or connectivity) | Check database logs and that the `midas_app` role can insert into `audit_logs`; the originating request is not rolled back, so investigate promptly |
| Recurring transactions not generated | Scheduler disabled or failing | Check `SCHEDULER_ENABLED`; look for `recurring tick error` and `recurring template paused after repeated failures`; check `midas_scheduler_runs_total` |
| Large exports abort | `EXPORT_MAX_DURATION_SECONDS` cap hit (`transaction export exceeded its time cap`) | Narrow the date range; raise the cap only if the database is healthy |

## Escalate

Contact the maintainers with: the time window, the affected `X-Request-Id` values, the output of
`/health`, the relevant log lines (already redacted), and the `midas_http_requests_total` rows
for the failing route. Never paste `.env` contents, tokens or `METRICS_TOKEN`.

## After

- If this was an incident, record what happened and the fix in the session log or tracker, and
  add a row to the table above when the cause was not listed.
- The rate-limit store is per process. This runbook assumes a single API instance; with several
  instances limits are applied per instance (see "Rate limiting" in README.md).
